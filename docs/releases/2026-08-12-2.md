## Scope

This release repairs the complete guest-account reservation lifecycle found by
browser-driven testing:

- reuse the guest profile created by an anonymous reservation when the same
  person creates an email account;
- link matching reservations and invoices to that account/profile;
- expose eligible Edit request and Cancel request controls in the account
  reservation center;
- render date-only reservation values without local-timezone day drift.

This is one connected lifecycle correction. No payment authorization, provider
configuration, database model, migration, middleware, or OAuth setting changed.

## Manual Browser Verification

Tested at `http://127.0.0.1:8000/` through the in-app browser using a new,
clearly identified QA customer:

1. Submitted an anonymous reservation request for November 10-13, 2026, two
   guests.
2. Confirmed the secure-payment handoff showed request
   `MLADIS-REQ-20260812-000041`, the correct dates, three nights, a $180 stay
   hold, and a $200 damage-deposit hold. No money was charged.
3. Created a new email account using the reservation email.
4. Confirmed one user, one customer profile, and one linked reservation.
5. Opened Edit request from the account UI and changed the reservation to
   November 11-15, 2026, three guests.
6. Confirmed the UI and database showed four nights and a recalculated $280
   stay hold / $480 combined total.
7. Opened Cancel request from the account UI, supplied a reason, and confirmed
   cancellation.
8. Confirmed the canceled state persisted, and Edit/Cancel were no longer
   offered.
9. Signed out and confirmed the reservation detail URL redirected to login with
   its return path preserved.
10. Confirmed no browser console warnings or errors during the lifecycle.

The reversible QA account, profile, and reservation records were removed from
the local database after verification.

## Known Limitations

- The browser lifecycle stopped at the secure-payment handoff. It did not make a
  real charge or authorization.
- External OAuth provider consent screens and production email delivery are not
  mutated as part of this release; their automated contracts passed.
- Full-site functionality remains governed by
  `docs/qa/full-site-functional-verification-plan.md`; this release proves the
  public request and email-account reservation lifecycle, not every platform
  function.
